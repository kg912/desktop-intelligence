Sandbox Architecture

Complete design and implementation reference for sandboxing every tool call in Desktop Intelligence, built toward a two-backend end state: @anthropic-ai/sandbox-runtime shipping now as the default for every tool call, and microsandbox as a second backend for genuinely untrusted heavy execution (arbitrary repo clone + build + test), adopted only after a benchmark gate on the actual target hardware. This revision adds the backend abstraction and benchmark protocol needed so Phase 0 code never has to be rewritten to accommodate Phase 4.

01 Overview & Motivation

Desktop Intelligence currently executes every tool call — LLM-generated Python code, custom MCP servers, and (per the Multi-Agent spec) future shell/code-execution steps — directly on the host, at the full privilege level of the logged-in user. Two concrete gaps were found in the actual codebase, not hypothetical ones:

FileCurrent behaviorWhy it's insufficient
PythonWorkerService.ts validatePythonCode() regex-blocklists import os, eval(, open(, etc. before running code in a persistent python3 worker. Regex blocklisting on source text is trivially bypassed. Application-level heuristic filtering, not kernel enforcement.
McpServerManager.ts Spawns every enabled MCP server as a raw stdio child process. No filesystem or network restriction. A malicious or prompt-injected MCP server runs with full host rights.
Governing principle: every process executing anything derived from an LLM's output must be treated as untrusted and structurally confined by the OS kernel — uniformly, whether the call originates from single-model mode or a Multi-Agent Orchestration worker.

This revision commits to a two-backend end state: srt for the always-on default (every Python execution, every MCP server), and microsandbox for the narrower, heavier case of running genuinely untrusted arbitrary code — a cloned repo in an unknown language with installable dependencies — which srt was never designed to solve. Section 05 defines the abstraction that lets both exist behind one interface from day one, so shipping srt now doesn't create rework later.

02 Threat Model

In scope

  • A hallucinated or buggy LLM tool call reading/writing/deleting outside its intended working area
  • A prompt-injected agent attempting to read credentials and exfiltrate them over the network
  • A malicious or compromised third-party MCP server attempting the same
  • LLM-generated Python attempting to shell out, open sockets, or escape its matplotlib/numpy/scipy sandbox
  • A runaway process (fork bomb, infinite loop, memory leak)
  • Arbitrary, multi-language, dependency-installing code from an untrusted source (e.g. a cloned repo) — the specific case microsandbox exists for

Explicitly out of scope

  • A kernel-level zero-day exploit against the host (both srt and, to a lesser extent, microsandbox's shared-hardware-but-separate-kernel model reduce but don't eliminate this)
  • Supply-chain compromise of Desktop Intelligence's own build pipeline
  • Physical access to the machine
  • A user deliberately disabling the sandbox for a specific server (a supported, logged, explicit action)

This is a defense-in-depth design for a local, single-user desktop app, not a multi-tenant cloud platform. That framing is why Docker stays rejected as a default (Section 12) even though it addresses part of this model.

03 Key Decisions

Default sandbox engine
@anthropic-ai/sandbox-runtime (srt)
OS-level (Seatbelt on macOS), no container/VM overhead, programmatic Node API, purpose-built for exactly this problem. Ships in Phase 0.
Heavy/untrusted execution backend
microsandbox — committed, gated on benchmark results
Confirmed real (YC F26, Apache 2.0, embeddable TS/Python/Rust SDK, no daemon/no root, secrets-substitution, spawn-sandboxes-from-sandboxes primitive). Groundwork ships in Phase 0 via the backend abstraction (Section 05) so adopting it later is additive. Actual adoption timing depends on Apple Silicon/HVF benchmarks (Section 14), not the vendor's Linux/KVM marketing figures.
Integration point
Single SandboxService, pluggable backends
One choke point every caller uses. Backend selection (srt vs. microsandbox) is an internal routing decision behind a stable interface — call sites never reference a backend directly.
Filesystem default (srt)
Deny-write-by-default, explicit-deny-read baseline
srt's write policy is deny-by-default but read is allow-by-default — must opt out per path. A maintained baseline denylist covers all known credential locations. See Section 07.
Network default (srt)
Deny-all, explicit per-server allowlist
Each MCP server declares needed domains in a manifest, reviewed by the user before first run.
Resource limits (CPU/RAM)
Not provided by srt — separate ResourceGovernor
srt has no cgroups-equivalent. A lightweight wall-clock + RSS-polling governor is required. (microsandbox, notably, provides real quotas per-VM — a secondary benefit if Phase 4 ships.)
Untrusted content into shell commands
Never interpolate — write to file, reference path
srt's API wraps a shell string, not argv. Concatenating LLM output into it is an injection surface independent of the sandbox boundary.
Explicit sandbox bypass
Per-server, explicit, logged — never global
A deliberate per-server toggle with a persistent warning indicator, never an app-wide switch.

05 Backend Abstraction & Routing Policy groundwork — ships Phase 0

This is the piece that makes "srt now, microsandbox later" true in practice rather than aspiration. Every caller depends on one interface; which backend actually runs is an internal decision, not something PythonWorkerService or McpServerManager ever needs to know about.

// src/main/services/sandbox/types.ts

interface SandboxRunSpec {
  workspaceDir:      string
  command:           string            // fixed, app-controlled — see Section 08
  image?:            string            // used only by MicrosandboxBackend
  executionProfile:  'lightweight' | 'untrusted-heavy'
  allowedDomains:    string[]
  allowWrite:        string[]
  denyRead:          string[]          // merged with BASELINE_DENY_READ, Section 07
  timeoutMs:         number
  maxRssMb:          number
}

interface SandboxRunResult {
  stdout: string
  stderr: string
  exitCode: number
  backend: 'srt' | 'microsandbox'
}

interface SandboxExecutionBackend {
  readonly name: 'srt' | 'microsandbox'
  initialize(): Promise<void>
  run(spec: SandboxRunSpec): Promise<SandboxRunResult>
  shutdown(): Promise<void>
}

// src/main/services/SandboxService.ts
class SandboxService {
  private srt: SandboxExecutionBackend            // SrtBackend — always active
  private microsandbox: SandboxExecutionBackend | null  // null until Phase 4 gate passes

  async run(spec: SandboxRunSpec): Promise<SandboxRunResult> {
    if (spec.executionProfile === 'untrusted-heavy') {
      if (!this.microsandbox) {
        throw new Error('untrusted-heavy execution requested but microsandbox backend is not enabled')
      }
      return this.microsandbox.run(spec)
    }
    return this.srt.run(spec)   // default path — everything today uses this
  }
}

Routing policy

  • 'lightweight' (default, used everywhere today) → always SrtBackend: Python worker, every MCP server, standard tool calls
  • 'untrusted-heavy' (explicit opt-in, only meaningful once Phase 4 ships) → MicrosandboxBackend: repo-clone-and-execute tasks, Multi-Agent workers explicitly flagged as needing package-install freedom in an unknown language
  • Requesting 'untrusted-heavy' before Phase 4 ships throws rather than silently falling back to an unsandboxed or under-sandboxed path — a missing capability must fail loudly, not degrade quietly
Phase 0 ships SrtBackend and a MicrosandboxBackend stub that satisfies the interface but throws on run(). This is deliberate: it means the call sites (PythonWorkerService, McpServerManager, the future Multi-Agent proxy) are written once, against the interface, and Phase 4 is purely "implement the stub's internals" — not a design change touching code that's already shipped and stable.

06 The Five Layers (SrtBackend)

Defense in depth for the active, default backend. No single layer is load-bearing alone.

L1
OS-level enforcement — srt (Seatbelt)
Kernel-enforced filesystem and network restriction on the whole process tree, applied at spawn time. Detailed in Section 07.
L2
Resource governance
Wall-clock timeout + RSS polling, since srt provides neither. Detailed in Section 09.
L3
Workspace confinement
Dedicated scratch directory per server/chat, backed by L1's allowWrite — belt and suspenders, not the actual boundary.
L4
Network allowlisting per tool
Declared manifest, reviewed by the user before first run. Detailed in Section 10.
L5
Audit & anomaly surfacing
Every denial logged; credential-denylist hits also surfaced in-app. Detailed in Section 11.

07 Layer 1 Deep Dive: srt — The Read/Write Asymmetry verified

The single most important detail in this document. From srt's own documentation:

Write access is deny-by-default — only paths in allowWrite are writable.

Read access is allow-by-default — everything is readable unless listed in denyRead.

A naive integration that only sets allowWrite leaves every file on disk still readable, including ~/.ssh/id_rsa, browser cookie databases, and cloud credential files.

Required baseline denyRead list

const BASELINE_DENY_READ = [
  '~/.ssh', '~/.aws', '~/.config/gcloud', '~/.docker/config.json',
  '~/.kube/config', '~/.netrc', '~/.npmrc', '~/.pypirc', '~/.gnupg',
  '~/Library/Keychains',
  '~/Library/Application Support/Google/Chrome/*/Cookies',
  '~/Library/Application Support/Google/Chrome/*/Login Data',
  '~/Library/Cookies', '~/.gitconfig', '~/.docker',
  '~/Library/Application Support/desktop-intelligence/settings.json'
]
Self-referential risk: Desktop Intelligence's own SettingsStore holds OpenRouter/NVIDIA/API keys on disk. That file must itself be in the baseline denylist.

08 Shell-String Construction & Injection Risk verified

Confirmed API: SandboxManager.wrapWithSandbox(command: string) takes a single shell string, executed with spawn(sandboxedCommand, { shell: true }) — not an argv array.

Never interpolate LLM-generated content directly into the command string. The sandbox restricts what the resulting process can touch; it does not sanitize the command line that produces that process.
  • Write LLM-generated code to a fixed-name file inside the workspace ({workspace}/_exec.py) via fs.writeFileSync
  • Build the command from fixed, app-controlled paths only: python3 ${workspacePath}/_exec.py
  • For any dynamic MCP arg, use a vetted shell-quoting library (e.g. shell-quote), and treat it as a code-review flag

09 Layer 2: Resource Governor not provided by srt

Confirmed via the source tree: no CPU/memory/disk quota module exists in sandbox-runtime. Seatbelt is access control, not cgroups.

class ResourceGovernor {
  private wallClockKill(pid: number, timeoutMs: number): void
  private memoryWatch(pid: number, maxRssMb: number): void  // pidusage, 1s poll
}
Not a hard boundary — a fast memory spike could beat a 1s poll. If true hard quotas become a hard requirement, that's an argument for routing that specific workload through MicrosandboxBackend (Section 13), which does provide per-VM resource limits, rather than trying to bolt cgroups onto macOS.

10 Layer 4: Network Policy & the MCP Sandbox Manifest verified

srt's network isolation is allow-only — empty allowedDomains means zero network access, enforced via an HTTP + SOCKS5 proxy on localhost.

{
  "name": "brave-search",
  "command": "npx", "args": ["-y", "@modelcontextprotocol/server-brave-search"],
  "sandboxProfile": {
    "allowedDomains": ["api.search.brave.com"],
    "allowWrite": [],
    "bypassSandbox": false
  }
}

User reviews requested domains/paths before a server is first allowed to run.

What network allowlisting does not do

No TLS inspection on the encrypted payload — a compromised process can still exfiltrate to any domain on its allowlist if that domain accepts arbitrary input. Keep allowedDomains narrow and purpose-specific.

11 Layer 5: Audit & Observability

  • Every srt violation appended to the existing trace as sandbox_violation: { serverId|worker, path|domain, kind, backend, timestamp }
  • Baseline-denylist hits surfaced as an in-app notification, not just logged
  • Routine violations logged only, visible in the existing observability panel

12 Rejected Alternatives — and Why

nono
Real, well-built, same OS-primitive category as srt. But network control is documented as all-or-nothing block — no domain-level allowlisting. Most MCP servers need some network, not none.
Docker (as default layer)
Shares the host kernel — doesn't stop a kernel exploit despite isolation optics. Requires Docker Desktop running as a hard dependency. Heavier boot overhead for the common case (every tool call). Remains a documented fallback for Phase 4 only if microsandbox fails its benchmark gate — see Section 14.
Per-chat ephemeral sandbox + template system
Directionally reasonable, but scope creep relative to the gaps in Section 01. Deferred to a later iteration once Phase 0–2 ship.
Regex/blocklist code validation (current state)
Actively replaced, not extended — validatePythonCode() is deleted once SrtBackend wraps the worker.

13 Microsandbox: Verified Capabilities & Multi-Agent Fit verified against microsandbox.dev

Confirmed directly from the vendor site, not secondhand research:

  • YC-backed (Combinator F26), Apache 2.0, no telemetry, free forever for local/self-hosted use — cloud sync is a separate paid layer, irrelevant to this local-first design
  • Embeds as a library — no daemon, no root requirement, unlike Docker's always-on root dockerd. This is a concrete architectural advantage, not just a speed claim
  • Secrets substitution: real key values never enter the guest VM; a placeholder is swapped in and the real value injected only on a verified TLS handshake to an allowlisted host
  • TypeScript/Python/Rust SDKs; OCI-compatible images (existing Docker images work unchanged)
  • Spawn-sandboxes-from-sandboxes: code running inside one microsandbox can spawn peer sandboxes, each with its own network policy and secrets

Why this matters specifically for Multi-Agent Orchestration

The spawn-from-sandbox primitive maps almost directly onto MULTI_AGENT_SPEC.html's dynamic worker model (Section 04/06 of that spec): each orchestrator-spawned worker agent could be its own microsandbox instance, with snapshot/fork used to warm one base image once and fork N parallel workers quickly rather than cold-booting each independently — directly relevant given the default max-agent cap of 4. This is a good reason to prioritize the benchmark in Section 14 sooner rather than later if the Multi-Agent Phase 2 timeline and this timeline start to overlap, but it does not change Phase 0's priority.

The published benchmark ("~320ms boot, faster than Docker's 463ms") is measured bare-metal Linux/KVM. Apple Silicon uses Hypervisor.framework (HVF) via libkrun — a different backend, with no published number for your actual target hardware. Section 14 exists specifically to replace that vendor figure with a real one from your machines before any adoption decision is made.

14 Benchmark Protocol & Go/No-Go Gate

The purpose of this section is to make Phase 4 adoption a data-driven decision made on your actual hardware, not a vendor-marketing-driven one. Run on both machines — the M1 Pro number matters more, since it's already the machine where the project's known performance issues surface (see project history: persistent stutter, unresolved rAF loop investigation).

Benchmark tasks

IDTaskMethod
B1Cold boot latencySandbox.create() to first successful exec('echo hello') response. N=20 runs. Record cold (no image cache) and warm (cached image) separately.
B2Concurrent spin-upBoot 4 sandboxes simultaneously (matches the Multi-Agent default max-agent cap). Record wall-clock time to all 4 ready.
B3Snapshot/fork/restoreWarm one sandbox with a representative Python devkit image (numpy/pandas installed), snapshot it, fork 4 times, record fork-to-ready latency per fork.
B4Representative workloadClone a small real public repo, install its deps, run its test suite inside the sandbox. Record total wall time, and separately the same steps run unsandboxed, to get the actual overhead delta rather than a synthetic number.
B5Idle memory footprintRSS of the hypervisor/guest process per idle sandbox, at rest and with 4 concurrent.
B6M1 Pro concurrency ceilingIncrease concurrent sandbox count until CPU/memory contention or UI stutter becomes visible. Record the ceiling.

16 Implementation Scope

Foundation (Phase 0)

  • Pin @anthropic-ai/sandbox-runtime at an exact version
  • SandboxRunSpec / SandboxRunResult / SandboxExecutionBackend types (Section 05)
  • SrtBackend implements SandboxExecutionBackend — the only backend that does real work in Phase 0
  • MicrosandboxBackend stub — interface-conformant, throws on run() until Phase 4 gate passes
  • SandboxService routing logic (executionProfile → backend)
  • BASELINE_DENY_READ constant, unit-tested
  • Dependency check on startup, surfaced in Settings if missing

Resource Governor

  • ResourceGovernor: wall-clock kill + pidusage-based RSS polling

PythonWorkerService retrofit

  • Delete validatePythonCode() entirely
  • Write code to {scratchDir}/_exec.py, never shell-interpolated
  • Spawn via SandboxService.run({ executionProfile: 'lightweight', ... })

McpServerManager retrofit

  • Extend mcp.json with sandboxProfile
  • Every stdio spawn routes through SandboxService unless bypassSandbox: true
  • Manifest review UI; persistent bypass indicator

Benchmark (pre-Phase-4 gate)

  • Benchmark harness script(s) for B1–B6, runnable on both machines
  • Results recorded, go/no-go decision documented in progress.md before MicrosandboxBackend internals are written

Multi-Agent integration

  • LangGraph sidecar's worker tool calls proxy back to Electron over IPC into this same SandboxService
  • Revise MULTI_AGENT_SPEC.html's sandboxing decision card to point here

19 Appendix: Verified API Reference

srt (active, Phase 0)

import { SandboxManager } from '@anthropic-ai/sandbox-runtime'
import { spawn } from 'child_process'

await SandboxManager.initialize()   // once, at app startup

const sandboxedCommand = await SandboxManager.wrapWithSandbox(
  `python3 ${fixedScratchPath}/_exec.py`   // never build this from untrusted content
)
const child = spawn(sandboxedCommand, { shell: true, stdio: 'inherit' })
child.on('exit', (code) => { /* ... */ })

await SandboxManager.reset()   // optional, happens automatically on process exit
// Confirmed flat config schema — NOT nested under a "sandbox" key
{
  "network": { "allowedDomains": ["api.example.com"], "deniedDomains": [] },
  "filesystem": { "denyRead": ["~/.ssh", "~/.aws"], "allowWrite": ["./sandbox-workspace"], "denyWrite": [] },
  "enableWeakerNestedSandbox": false,
  "enableWeakerNetworkIsolation": false
}

microsandbox (Phase 4, pending benchmark gate)

import { Sandbox } from 'microsandbox'

const sb = await Sandbox.create('worker-1', {
  image: 'python:3.12-slim',
  network: { allow: ['pypi.org', 'files.pythonhosted.org'] },
  secrets: { OPENAI_API_KEY: process.env.OPENAI_API_KEY },
  volumes: [{ host: workspaceDir, guest: '/workspace' }],
})

const result = await sb.exec('python3', ['/workspace/_exec.py'])

// Snapshot/fork — relevant to Multi-Agent parallel worker spin-up, Section 13
const snap = await sb.snapshot()
const forked = await snap.restore('worker-2')

await sb.destroy()
Corrections applied to prior research: srt's method is wrapWithSandbox(command: string), not wrapCommand([cmd, args]). Config keys are flat, not nested under "sandbox". No permissions.allow/deny array syntax exists in this package (that belongs to Claude Code's separate settings.json). No httpProxyPort/socksProxyPort fields. No CPU/memory/disk quota mechanism in srt at all. The microsandbox snippet above reflects the vendor's own published SDK shape as of this writing — re-verify exact method names against whatever SDK version is actually installed, since it remains pre-1.0 software subject to change.
