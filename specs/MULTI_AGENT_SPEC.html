01 Overview & Motivation

Desktop Intelligence currently operates in single-model mode: one inference call per user message, one context window, sequential tool calls. This works well for conversational tasks but hits structural limits on complex, multi-step work.

Multi-agent orchestration mode allows a network of specialized agents to work in parallel, with reflection gates between steps and a synthesis phase at the end. The result is a system that can handle tasks that frontier web products (Claude.ai, ChatGPT, Gemini) literally cannot — not because of capability gaps, but because of architectural ones.

What single-model cannot do well

TaskWhy single-model failsHow multi-agent solves it
Analyze an entire large codebaseContext window fills before all files are readParallel agents each read a module; synthesizer assembles
Cross-verified researchOne model can't adversarially review its own outputCritic agent independently reviews with fresh context
Code + independent testsTests written by the same model that wrote the code confirm implementation, not correctnessTest agent never sees implementation agent's code
Long-horizon tasks50-step tasks hit context limits or degrade in qualityOrchestrator decomposes; each agent has a fresh window
Multi-perspective analysisOne model doing impressions of multiple viewpointsEach agent given a different system prompt / role
The differentiating demo: "Clone this GitHub repo, run the tests, identify the three highest-risk areas, and write a prioritized remediation plan." Claude.ai cannot do this. ChatGPT cannot do this. Desktop Intelligence, with its local filesystem access and multi-agent execution, can.

02 Key Decisions

These decisions were made during design and should not be revisited without good reason. Context for each is included.

Backend
OpenRouter only
Only provider with a unified API across 200+ models, enabling per-agent model routing within a single session. LM Studio, Ollama, NVIDIA are single-model by nature.
Orchestration runtime
Python sidecar (LangGraph)
LangGraph provides state machine primitives (reflection loops, retry, conditional branching, HITL pause) that would take weeks to rebuild correctly in TypeScript.
Sidecar communication
localhost HTTP + SSE
FastAPI on localhost:7823. SSE for event streaming back to Electron. Mirrors existing matplotlib worker pattern already proven in the codebase.
Agent count
Dynamic, orchestrator-decided
Orchestrator model decomposes the task and decides how many agents to spawn. User sets a hard cap (default: 4) and per-run budget cap (default: $0.50) as guardrails.
Model selection
Full OpenRouter catalogue, filtered
No curated shortlist — too much maintenance burden. Fetch /api/v1/models at runtime, filter by tool-call support + context length. Show price/1M tokens. Default: Llama 3.3 70B for orchestrator + reflection; user picks worker model.
Sandboxing (code execution)
Docker (opt-in, Phase 2)
E2B considered but adds cloud dependency and ongoing cost. Docker runs locally, no data leaves machine, user brings their own Docker Desktop. Not required for MVP — agents can read via Filesystem MCP without execution.
Per-chat system prompt
Deferred — decision pending
Useful for multi-agent but not blocking MVP. Each agent gets a role-specific system prompt from the orchestrator. Global system prompt applies as base.
Sidebar layout
Mutually exclusive panels
Chat sidebar and orchestrator plan pane cannot both be open simultaneously. Sending a task auto-collapses the chat sidebar. Opening the sidebar collapses the plan pane. Both collapse to a 40px dot rail, never to zero.

Sidecar process lifecycle

The Python sidecar follows the same pattern as the existing matplotlib worker. It is spawned from index.ts when the app starts (if OpenRouter is the active backend, or on first multi-agent run — decision pending). It runs a health check ping every 10 seconds and is restarted automatically on crash. On app quit, it is cleanly terminated — no orphaned processes. Port default is 7823, configurable in settings.

Sidecar binary strategy

Two options remain open: pyinstaller frozen binary (bundled in DMG, no Python requirement) vs. system Python + venv (simpler to develop, requires Python 3.11+ installed). Decision must be made before shipping. Frozen binary is preferred for the distributed app.

04 Agent Roles

RoleRunsDefault ModelPurpose
Orchestrator Once, at start meta-llama/llama-3.3-70b Receives task, decomposes into AgentStep[], emits orchestrator_plan event. Enforces max-agent cap. Model must be good at structured JSON output.
Worker agents 1–N in parallel User-configured (filtered OpenRouter catalogue) Execute individual subtasks. Each gets its own context window, role-specific system prompt, and can call MCP tools. Most expensive — model choice here drives cost.
Reflection agent After each worker meta-llama/llama-3.3-70b Receives goal spec + worker output. Returns score (1–5), passed (bool), reason (string). Cheap — pass/fail scoring is simple. Same model as orchestrator is fine.
Synthesizer Once, at end User-configured (default: Qwen3 235B or similar) Receives all agent outputs + reflection results. Produces final answer with inline provenance markers. Runs on a large combined context — needs good long-context performance.
On Llama 3.3 70B: Validated by Databricks engineering teams for agentic workloads. Strong at structured JSON plans, tool calls, and instruction following. Fast and cheap enough that the orchestration overhead doesn't feel punishing. Good default — not a controversial pick.

06 Cost Control & Model Selection

The problem

A runaway orchestrator could spawn 6+ agents and burn significant budget before the user notices. OpenRouter's free tier for some models silently times out rather than returning an error (observed with NVIDIA). Multiple safeguards are required.

Three-layer protection

LayerMechanismDefault
Hard agent cap Setting in Multi-Agent config. Baked into orchestrator system prompt: "You may spawn a maximum of {maxAgents} agents." Sidecar also enforces — if orchestrator_plan arrives with more agents than cap, sidecar rejects and re-plans. 4 agents
Per-run budget cap Dollar limit set before sending. Sidecar tracks cumulative spend using OpenRouter usage fields in streaming responses. When cap is hit: no new agents spawned, running agents finish current response, synthesis runs on partial output, UI shows "Budget cap reached" badge. $0.50
Pre-flight approval Orchestrator plan event received → UI shows plan tree + cost estimate range → user approves before any worker agents fire. Same HITL component pattern. Cost estimate is a range (e.g. "$0.04 – $0.18") with worst-case prominently shown. Estimates are rough — token counts for tool calls are unknown pre-execution. Always shown

Model selection UI

No curated shortlist — too much ongoing maintenance as models are added/deprecated on OpenRouter. Instead, fetch /api/v1/models at runtime and present a filtered dropdown with three user-configurable filters: sort by price ascending, minimum context length, requires tool-call support. This cuts 200+ models to ~20 relevant ones. Price per million tokens is shown next to each model name. Claude Sonnet, Gemini Pro etc. are available but not defaulted — if a user wants to spend that, it's their call.

Role tiers: Rather than per-agent manual selection (impractical since agent roles are dynamic), expose four model slots: Orchestrator, Worker agents (global for all workers), Reflection, Synthesizer. User picks one model per slot. All worker agents in a run use the same worker model.

07 HITL Expansion for Multi-Agent

The existing HITL system (4 permission layers: per-server persistent, per-chat require-all, per-chat bypass-all, inline popup) is the right foundation. Multi-agent mode requires three additions.

AdditionWhat changes
Agent identity on popup The existing popup shows tool name + server + args. Multi-agent adds: which agent triggered it (role + model). "Analyzer Agent (claude-3.5-sonnet) is requesting access to read_file." Without this the user has no context for why the tool is being called mid-run.
Per-agent permission scoping Trust/block at the agent level within a run, not just at server level. A user may want to trust the Researcher agent fully but keep the Analyzer agent gated, within the same run. New layer: agent-level trust, sits between per-chat and per-server.
Non-blocking parallel pauses Current HITL is fully blocking — one popup, everything waits. In multi-agent, Agent 1 hitting a permission gate must NOT freeze Agent 2 if they are independent. Sidecar handles per-agent pause/resume. UI shows multiple simultaneous pending approvals — each paused step highlighted in the plan pane, each with its own resolve action. Input bar names the specific agent waiting.

HITL timeout

If a HITL pause goes unanswered, the sidecar auto-denies the tool call after a configurable timeout (default 5 minutes) and emits a failure event for that agent. The run continues with the other agents and synthesizes on partial output.

08 Implementation Scope

Check off items as implemented. Do not modify objectives retroactively. This is the source of truth for what "done" means.

Foundation — Database

  • conversations table: add mode column ('single' | 'multi-agent')
  • conversations table: add agent_graph column (JSON)
  • conversations table: add execution_trace column (JSON — ordered AgentEvents)
  • conversations table: add run_status column ('idle' | 'running' | 'paused_hitl' | 'completed' | 'failed')
  • SQLite migration script written and tested
  • Migration runs automatically on app start (version-gated)

Foundation — Shared Types

  • AgentEvent discriminated union defined in shared/types.ts (all event types per section 05)
  • AgentStep type defined
  • MultiAgentConfig type defined (model slots, reflection threshold, max retries, max agents, budget cap)
  • SandboxConfig type defined (for Phase 2 Docker — repo URL, network policy, write-back flag)

Foundation — IPC Channels

  • multi-agent:start — accepts task + config, starts sidecar run, returns run ID
  • multi-agent:event-stream — SSE from sidecar forwarded to renderer
  • multi-agent:hitl-respond — accepts { runId, agentId, approved }, unblocks paused agent
  • multi-agent:abort — cleanly cancels in-progress run
  • multi-agent:sidecar-status — returns 'running' | 'stopped' | 'error'
  • Synthetic ready-state response for all channels when sidecar is not running

Foundation — Sidecar Lifecycle

  • Python sidecar spawned from index.ts (reference: existing matplotlib worker)
  • Health check ping loop (every 10s) with auto-restart on crash
  • Clean shutdown on app quit — no orphaned Python processes
  • Port conflict detection (localhost:7823 default)
  • Sidecar binary strategy decided: pyinstaller vs system Python
  • Sidecar logs routed through observability system with [Sidecar] prefix

Python Sidecar — Infrastructure

  • FastAPI server on localhost:7823
  • POST /run — task + config → run ID
  • GET /run/{id}/stream — SSE AgentEvent stream
  • POST /run/{id}/hitl — resume paused agent
  • DELETE /run/{id} — abort
  • GET /health — ping
  • OpenRouter API key passed from Electron settings

Python Sidecar — Orchestrator

  • Decomposes task into AgentStep[] using fast model
  • Emits orchestrator_plan before any agents start
  • Enforces max-agent cap — rejects and re-plans if exceeded
  • Supports sequential and parallel step execution
  • Handles partial failure — one agent failing does not abort run

Python Sidecar — Worker Agents

  • Each agent gets own context window (no shared state bleed)
  • Model per role configurable in MultiAgentConfig
  • Agents can call MCP tools (passed through from Electron's McpServerManager)
  • Agent output is structured: role, output, tool calls, token count, cost
  • Emits agent_start, agent_token (streaming), agent_complete

Python Sidecar — Reflection

  • Reflection agent receives goal spec + worker output
  • Returns { score: 1-5, passed: bool, reason: string }
  • Configurable pass threshold (default ≥ 3)
  • Failed reflection triggers automatic retry with failure context injected
  • Max retry limit per agent (default: 2) → task_failed if exceeded
  • Emits reflection_start, reflection_result, retry

Python Sidecar — Synthesis

  • Synthesizer receives all agent outputs + reflection results
  • Produces final answer with inline provenance markers ([1.1], [1.2])
  • Streams token by token via synthesis_token
  • Emits task_complete with total cost + token summary

Python Sidecar — HITL

  • Pauses agent execution when tool requires approval
  • Emits hitl_pause with agentId, role, full tool args
  • Other independent agents continue running during pause
  • Timeout: auto-deny after 5 min (configurable)

Frontend — Multi-Agent Mode Button

  • Glowing button next to "Require Permissions" in InputBar
  • Only visible when OpenRouter is active backend
  • Click toggles mode on/off for current session
  • Inactive: subtle red-tinted outline
  • Active: pulsing glow ring (Apple Intelligence-style), input box picks up breathing border glow

10 Docker Sandboxing (Phase 2)

Without sandboxing, agents doing real work — cloning repos, running code, writing files — operate directly on the host machine. One hallucinated path causes real damage. Sandboxing provides an isolated, ephemeral environment where agents can execute freely and fail safely.

Phase 2 only. MVP ships without Docker sandboxing. Agents read local files via the existing Filesystem MCP (already restricted to allowed directories), do web research, and call APIs. That's already more capable than any frontier product. Docker execution is added as an opt-in capability flag in Phase 2.

Why Docker over alternatives

OptionVerdictReason
Docker container per run ✓ Chosen Proper isolation, runs locally, no data leaves machine, user controls it. Mirrors existing subprocess patterns (matplotlib worker, LangGraph sidecar).
E2B (e2b.dev) Deferred 78ms sandbox spin-up, Firecracker-based, used by Perplexity and Manus. $100 free credit. But adds cloud dependency (breaks local privacy story) and ongoing per-sandbox cost that user can't control. Available as alternative if user provides their own E2B API key — same pattern as OpenRouter/Brave.
macOS sandbox-exec Rejected Deprecated Apple API, not a real security boundary for code execution, cannot safely run arbitrary agent-generated code.
Firecracker / microVM Overkill Strongest isolation but complex setup, requires Linux, overkill for a desktop app.

Docker sandbox lifecycle

1
Pre-flight config
User sees sandbox config in pre-flight approval screen (same screen as cost estimate). Options: repo URL to clone, network policy (GitHub only / full / none), write-back to repo (off by default), credential injection (explicit enable required, never automatic).
2
Container spin-up
Sidecar calls docker run with a base image (Python + git + common tools). Nothing from the host filesystem is mounted. Container gets a unique name tied to the run ID. Emits sandbox_start AgentEvent with containerId.
3
Agent execution inside container
Agents execute shell commands via docker exec. stdout/stderr streamed back as sandbox_output events — visible in the agent lane as a terminal-style block. Agents can clone repos, run tests, write files — all inside the container boundary.
4
HITL for destructive actions
Write operations (git commit, file write outside /tmp) trigger a HITL pause even if the agent has general approval. User sees the specific command about to run. Same approval popup pattern with agent identity shown.
5
Output extraction
On run complete, sidecar copies specified output paths from container to a local staging directory before teardown. If write-back is enabled, user reviews diff and explicitly approves before any git push.
6
Container teardown
Container is destroyed on run completion, abort, or crash. Emits sandbox_end with exit code. No persistent state. If the app crashes mid-run, a cleanup routine on next launch kills any orphaned containers tied to Desktop Intelligence run IDs.

Docker AgentEvent additions (Phase 2)

sandbox_start{ agentId, containerId, image }
sandbox_output{ agentId, stdout, stderr, command }
sandbox_hitl{ agentId, command, reason } — destructive action requires approval
sandbox_end{ agentId, containerId, exitCode }

Settings additions (Phase 2)

  • Docker availability check on settings open (show warning if Docker Desktop not running)
  • Base image selector (default: python:3.11-slim + git)
  • Max container lifetime (default: 10 min — hard killed after)
  • E2B API key field (alternative to local Docker — user brings own key)
  • Cleanup orphaned containers button

12 Definition of Done

A multi-agent run is considered complete and shippable (Phase 1–4) when all of the following are true:

D1A task with ≥2 parallel agents completes end-to-end on OpenRouter
D2At least one reflection failure + automatic retry cycle works without user intervention
D3Final synthesis contains ≥1 provenance tag clickable to source agent
D4HITL pause on one agent does not block a parallel independent agent
D5Full execution trace appears in observability logs post-run
D6Layout state machine transitions are animated and correct (all 6 states)
D7Cost counter per agent shows accurate token usage from OpenRouter response
D8Run can be aborted cleanly at any point — no orphaned sidecar processes
D9Budget cap triggers correctly — partial synthesis delivered, no overspend
D10Multi-agent mode button hidden when non-OpenRouter backend is active
